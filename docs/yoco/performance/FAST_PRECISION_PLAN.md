# Fast 多精度复用与 FP8 性能优化计划

2026-09-10新增进展：[routed直接FP8量化与Top-8 logits候选已接入](fast-fp8-route-direct-20260910/REPORT.md)，完成内核/模型数值和局部性能验证。下文保留初始计划与历史判断；这两项已完成，LM head、latent、lambda额外量化及FP8 KV仍为后续候选。

日期：2026-09-09，状态更新于2026-09-10。初始计划之后，按用户要求优先实施公共路径复用，进展见[实施报告](fast-precision-reuse-20260909/REPORT.md)。[同条件Mooncake 2×对照](fast-bf16-mooncake-f2-20260909/REPORT.md)已补测BF16，当前FP8相对BF16吞吐高13.65%；下列更高提速目标仍是待验证的工程目标。

[训练/推理精度审计](fast-precision-audit-20260910/REPORT.md)确认，两端FP8投影覆盖基本一致。后续优先研究routed直接FP8量化，并重评已有的Top-8 logits benchmark候选，再独立评估LM head、latent及配合融合的lambda量化。Fast此前已完成路由融合、删除dense中间量和额外Top-K/cast；重评候选只针对当前仍保留的完整softmax，不能重复计算已有收益。原计划中保留lambda等BF16的约束对应原数值语义复用；用户允许小误差后的新候选按审计中的独立质量门槛验证。当前B200 FA4不能直接启用FP8 KV，需要另行适配。

目标是在 YOCO Fast 中共用与精度无关的优化，让 BF16 和 block-128 FP8 都受益，并验证 FP8 相对当前 BF16 的端到端收益。第一阶段限定 YOCO L3 step28000、B200 SM100、TP1/DP1/EP1。FP16、MXFP8、FP4 可以继承接口和测试方法，但它们的兼容性、性能和质量需要另行验证。

## 1. 已有证据与尚缺的比较

- [首次同卡 FP8/BF16 对照](fp8-vs-bf16-20260909/REPORT.md)：旧 FP8 低并发比 BF16 慢约 10%–23%，存在分派、padding、量化与融合缺口。
- [有效路由行优化](fast-fp8-sparse-20260909/REPORT.md)：已经减少无效行量化，并融合路由权重处理。
- [最新分派与布局优化](fast-fp8-dispatch-f2-20260909/REPORT.md)：已经实现 M≤16 的 Triton 分派、M=3/4 的专家分组、scale 缓存、PSUM/scatter/scale 打包融合和相应路径的 CPU 标量同步消除。209 项测试通过。
- 最新 FP8 的 ISL128/OSL128、C1 为 159.87 tok/s，C4 为 481.70 tok/s；历史 BF16 对应为 159.72、412.96 tok/s。它们是不同轮次的测量，只提示优化方向，不能代替当前源码的配对比较。
- 前轮 Mooncake 2× 的 1094.75→1407.82 tok/s（+28.60%）是 FP8 内部优化收益。现已补测相同2×条件的BF16：1238.79 tok/s，对应当前FP8 1407.84 tok/s（+13.65%）；历史BF16的1.2×结果不参与该比例计算。
- 小 M 更换 GEMM 后端已有非 bitwise 差异，batch8 有生成 token 变化；有限性测试通过，任务质量尚未评估。

现有实现基于 `fhb-dev-9-8`，HEAD `511fbed3f75f0fd18a4f93194ca832db2c723f98` 加本地改动。执行时冻结实际完整源码和补丁，不能只记录 HEAD。

## 2. 哪些可以复用

| 层次 | 复用方式 | 需要区分的部分 |
| --- | --- | --- |
| YOCO 模型语义 | 共用路由规则、clamp、SwiGLU、路由权重位置、shared/routed 合并约定及参考实现 | 保留量化边界、输出 dtype 和舍入语义；移过量化操作会改变结果 |
| BF16 hidden 上的算子 | 共用适用的 RMSClip、RoPE、残差、LM head 和 attention 优化 | 按实际操作数 dtype 与设备能力启用；不能仅因模型设了量化就全部禁用 |
| 调度与图执行 | 共用静态 workspace、预热、CUDA graph 生命周期、缓存刷新和回退框架 | shape、布局、地址与所选 kernel 必须一致，分派不能引入设备到主机同步 |
| MoE 路由元数据 | 共用计数、有效行、前缀和、分组、gather 的逻辑和测试 | 不同后端的 padding、路由权重处理位置、scale 和 TMA 布局分别适配 |
| 投影融合 | 共用投影规划、checkpoint 名称映射、输入复用及验证方法 | 同精度输出可合并；FP8 Q/QKV 与 BF16 lambda 需要混合精度实现 |
| GEMM | 共用调优脚本、分派接口、实际 shape 采样与结果数据库 | BF16/FP8 的 tile、warp、stage、Tensor Core 指令、scale 布局及阈值分别调优 |
| FP8 量化 | FP8 路径之间共用量化/pack、加载阶段权重处理和 scale 缓存 | BF16 无此步骤；FP8、MXFP8、FP4 的数值格式与分块规则不能互换 |
| 验证与报告 | 共用输入、数值参考、负载、审计与性能表 | 每个精度、后端和测量轮次单独标注 |

不按代码行数承诺“复用百分比”。以一项通用优化能否同时进入 BF16/FP8 路径、能否由同一套测试覆盖作为复用标准。采用小范围接口抽取，避免在性能工作前先做全量框架重构。

## 3. 实施顺序

### P0：建立当前版本的 BF16/FP8 配对基线与耗时分解

1. 冻结当前 BF16 和 FP8 的源码、模型、精度设置、后端、图设置、GPU UUID 与客户端配置。
2. 先用当前 FP8 和 BF16 做同卡低并发对照，再补相同 Mooncake 2× 对照。每次只计时一个服务；BF16 如随通用优化发生变化，最终必须同步重测。
3. 用独立诊断请求采样实际 MoE/linear 的 M/N/K、路由分布和图 padding。M 是算子输入 token 行数，不等于客户端并发。
4. 分开统计 decode 和 prefill 的 W13、W2、shared expert、dense projection、量化/搬运、attention/KV、其余算子及主机空隙。吞吐计时不启用 profiler；处理重叠时不能把 kernel 时长之和当作墙钟时间。
5. 输出每个候选可影响的耗时比例与可达到的上限，按证据调整 P2–P4 的先后。

交付：当前版本的精度对照表、实际分派/融合覆盖表、耗时分解。此阶段首先回答“当前 FP8 到底比 BF16 快多少”。

### P1：整理可共用的 Fast 路径和验证契约

1. 审计 `yoco.py` 的 `quant_config is None` 条件，逐项记录是必要的权重格式限制，还是可改为操作数/功能能力检查的条件。
2. 保留已生效的 FP8 LM head、weighted RMSClip 等优化，不重复列作新增成果。
3. 在有第二个实际使用方时抽取公共接口：输入/输出 dtype、权重量化格式、scale 布局、shape、硬件、并行配置和回退规则。
4. 共用调优与计时入口；配置键区分 dtype、SM、M/N/K、路由特征与图模式。沿用按精度独立验证的阈值，不照搬 BF16 配置。
5. 对当前不支持的 TP/DP/EP、EPLB、模型形状保留原路径。Fast 改动涉及共用代码时运行相关 Align 回归。

交付：小范围公共基础代码和覆盖表；BF16 与 FP8 均无可重复的性能回退。

### P2：优先补齐 dense / shared-expert 的 FP8 缺口

1. **模型级 K/V 合并投影**：先处理同精度部分，共用输入量化与一次 GEMM；保留各逻辑输出的 block-scale 边界、checkpoint 映射及 ignore 规则。K/V 精度策略不同则回退。
2. **shared-expert 小 M 优化**：分别测 gate/up、clamped SwiGLU、激活量化与 down projection；尝试融合激活和量化、优化 FP8 权重/scale 布局及小 M GEMM。BF16 转置权重缓存的思路可以复用，但不能把该权重直接用于 FP8 kernel。
3. **其他小 M dense linear**：根据 P0 的热点选择投影，测量包含量化、布局转换和 GEMM 的整段时间。只缓存小型元数据或必要布局，不默认复制整套 BF16 专家权重。
4. **QKV/Q 与 lambda**：lambda 保持现有 BF16 精度。先评估输入读取和调用开销，只有占比足够才实现混合精度投影融合；不能通过量化 lambda 来冒充等价移植。

交付：每项的独立开关或可冻结源码快照、kernel 和完整服务消融。优先保留降低完整调用链时间的实现。

### P3：继续调优 FP8 MoE，分别处理 W13 与 W2

1. 在现有 M≤16 混合分派基础上，分别调 W13/W2 的 tile、warp、stage；扩大阈值必须有实测支持。
2. 必测 M=1/2/3/4/8/15/16/17/32/64/128/256/512/2048/8192，覆盖真实路由样本、分散路由和集中路由；同时检查图 padding 导致的实际 M。
3. 研究减少重复权重读取、过多小 kernel、W2 输出中间写回以及 gather/sum 开销；能够保持当前量化语义时再融合。
4. 基于实际设备能力评估其他已有后端，先检查它们是否支持 YOCO clamp、加权位置和 block scale，不能仅凭 GEMM 峰值替换完整 MoE。
5. 分派依赖已有 shape 或已有设备侧信息，不增加每步路由统计的 CPU 同步或在线调优。

交付：BF16/FP8 分别维护的配置与分派阈值、完整 MoE 计时、端到端消融；如 W2 已不再是主要瓶颈，优先级下调。

### P4：按瓶颈选择混合精度配置

若某些小投影的 FP8 量化开销仍超过收益，评估“专家 FP8、部分 dense/shared-expert BF16”。使用精确的模块列表记录策略，并作为独立配置报告显存、速度和质量，不能与原 block-128 FP8 点混记。

先完成现有 W8A8 block-128 路径；MXFP8/FP4 和 FP8 KV cache 是后续实验，会改变量化误差或 attention/KV 路径，不纳入本轮提速目标。长上下文若受 BF16 KV 读取限制，降低权重精度的收益会自然变小。

### P5：配对评测并更新维护表

按 P0 相同条件重新比较当前 BF16 与最终候选 FP8，同时保留“候选 FP8 / 优化前 FP8”的对照。独立列出通用优化给 BF16 带来的收益。

更新 [FP8.md](FP8.md) 和本轮结果报告，包含绝对吞吐、相对 BF16 比值、尾延迟、显存、数值结果、源码与原始数据引用。失败和未选中候选保留，不能按最快单次结果选择结论。

## 4. 性能目标与估算方法

以下是用于判断研发是否值得继续的工程目标，分母是最终同源码、同条件重测的 Fast BF16；不是已测成绩或性能保证。

| 工作负载 | 候选 FP8 / BF16 目标 | 约束 |
| --- | ---: | --- |
| 短上下文、C1–2 decode 为主 | 1.10–1.30× | 重点降低启动、量化、小 M GEMM 与重复读取成本 |
| C4–32 decode 为主 | 1.20–1.50× | 路由分布、批次利用率会显著影响结果 |
| GEMM 占比较高的 prefill | 1.30–1.60× | 用 TTFT/prefill 时间验证，不以单 GEMM 替代 |
| Mooncake toolagent 2× 同窗口回放 | 1.20–1.40× | 比较完整排空吞吐并同时报告 TTFT/ITL/E2E |
| 长上下文且 attention/KV 占主导 | 1.00–1.20× | hidden/KV 继续 BF16，收益可能很小 |

FP8 相对 BF16 在可量化矩阵的权重字节数和 Tensor Core 峰值上有接近 2 倍的潜在优势，具体受 scale、对齐、kernel 和硬件能力限制。整个服务还有未加速部分；模型加载显存从历史 61.04 GiB 降到 32.07 GiB 也不意味着请求时间减半。

用 P0 数据建立简化模型：`S = 1 / ((1 - f) + f / r + q)`。`f` 为 BF16 执行时间中可被此次量化加速的比例，`r` 为这部分实际加速比，`q` 为新增量化/布局等开销除以原 BF16 总时间。定义时避免重复计入已包含在 `r` 中的开销。

例如假设 `f=0.60, r=2, q=0.05`，整体仅约 `1.33×`；`f=0.80` 时约 `1.54×`。这些比例需要测量，公式不模拟 Mooncake 过载下的排队行为。各项优化的百分比不能简单相加。

## 5. 验证与评测协议

**数值验证先于计时。**布局与 scale 的等价转换维持 bitwise；GEMM 后端变更和跨精度比较报告实际误差，不设跨精度 bitwise 目标。以现有 MoE 实测相对 L2 低于 1e-3 为参考，拟将候选与相同量化语义参考实现的相对 L2≤1e-3 作为初始 kernel 门槛，并报告最大误差和异常输入；它不能证明模型质量，也不直接用于 FP8/BF16 全模型比较。

完整模型使用相同 token 序列、相同前缀进行 teacher forcing，比较固定 token 的 log-prob/NLL、PPL 以及必要的路由变化，分别做“候选/当前 FP8”和“候选/BF16”。覆盖短输入、8K、接近上下文上限和 batch8；所有输出必须有限。自由生成 token 一旦分叉，后续生成 log-prob 不再当作相同输入的误差。

拟增加固定的公开真实文本子集（优先 WikiText-103 test，冻结版本、文本/分词 hash 和切分）评估 NLL/PPL；在计时前固定质量回归判据并保留逐样本结果。此项与 Mooncake 性能回放分别执行。公开 Mooncake trace 只有长度、时间戳和前缀关系，不能用于模型任务质量结论。质量结果不清楚的候选保留为实验配置。

kernel 测试覆盖非连续输入、无效专家、分派边界、CUDA graph replay 和权重重新加载。共用代码变化运行 BF16 和相关 Align 回归；这不扩展 Align 的支持范围或 bitwise 声明。训练 backward 的精度与性能属于独立验证范围。

**低并发诊断：**继承 ISL128/OSL128、C1/2/4/8 以及 ISL8192/OSL128、C1 的点；按热点增加 C16/32、长 prefill、长 decode 用例，并分别报告。每档至少两次预热、三次测量，编译稳定后计时。

**Mooncake：**沿用 `run-aiperf-mooncake-trace` 协议和最新 2× 冻结 trace，源窗口 300–900 秒，3643 请求，到达约 300 秒，SHA256 `e0df4ca65eeac5daf8eb1529f2eb832b2e16ef8c76c53ce426a8ba1f1eb41310`。客户端上限两端均 2048、服务端 maxseq256；时间戳离线缩放，`synthesis-speedup-ratio=1.0`。每 case 使用独立 cache salt，保持前缀复用关系、请求长度、顺序和实际 token 计数一致。

执行前重新核对 trace、端点与进程所有权、GPU/node、软件与模型版本、运行中负载。已记录的服务 GPU2 UUID 为 `GPU-3c98295b-46bd-92b3-ef14-82b5e35524f7`，仅作为待核验目标。计时不与 GPU microbench 并行；保持其他工作负载和 GPU allocation。

比较使用同一物理 GPU，默认相同 memory utilization0.85、maxlen81920、max batched tokens32768、FA4、KV sharing、prefix/chunked prefill 和图设置；记录量化释放显存后实际 KV 容量的差别。如果 KV 驻留或驱逐显著不同，再增加相同 KV token 预算的隔离实验，区分计算收益与容量收益。

先做 50–100 请求 smoke，再做冻结窗口对照。最终采用 ABBA 轮换并形成至少三个配对，报告中位数和波动。每次只测一个实现；轮次内固定条件，不同时测试 Fast/Align/Qwen 三者。

每个 case 要求请求全部成功、无输出长度不匹配、无调度退化、lag P99≤500ms、不触及客户端并发上限、无超过5秒的指标空洞、无新增 GPU 错误，且所有队列排空。若任一客户端触顶，调整后必须两端一起重测。首轮出现新增 JIT 则保留为预热记录。

报告输出 tok/s、TTFT/ITL/E2E P50/P95/P99、调度 lag、并发峰值、服务端队列、prefix hit、显存和排空尾部。当前 2× 窗口属于过载诊断；若需要稳定容量结论，另设延迟 SLO，使用至少 600 秒实际到达窗口并进行完整排空和重复验证。

## 6. 完成标准

1. BF16 和 FP8 可共用的功能由明确的能力检查和测试覆盖，已支持路径不出现可重复回退。
2. FP8 相对当前 BF16 的收益由同条件配对数据支撑，目标未达到时如实说明瓶颈和差距。
3. 数值/质量结果与性能同时交付；吞吐提升不替代正确性验证。
4. 每项收益可由源码快照和独立消融复现，维护表链接完整证据。
5. 保留现有服务与 GPU allocation，在隔离的验证进程中完成新实现的检查。

# YOCO async：长输出、16K 输入与 C16/C32 补测

2026-10-22。实验分支 `fhb-dev-yoco-async-scheduling-20261022`，
在 `abcade593a` 上扩展压测工具。完成同 GPU 原生 ABBA 重复对照。

本轮提交 `c183d6568e` 已随异步分支合入 `fhb-dev-aligndeepinfer-startpoint`。
以下性能数据仍来自原冻结配置；与当前BF16 router默认的组合收益需单独测量。

**结论：短输入、512/1024 输出、C16/C32 有可重复的吞吐提升（+4.93%～+13.14%）；
16K 输入没有稳定正收益（汇总 −4.38%～−0.39%）。平均 TTFT 有代价，async 继续显式启用。**

## 固定协议

在正式结果出现前固定配置和判据，原始计划为 `attempt6/PLAN.json`。
同一 B200，顺序 sync-a1 → async-b1 → async-b2 → sync-a2。
每轮短输入/16384-token 输入 × 512/1024 输出 × C16/C32，每格两次预热、三个正式 seed。
相同三个 seed 在第二组重复；它们不是六个独立 prompt 样本，不据此声称统计显著性。

采用描述性的重复收益判据：两组配对各自的聚合吞吐提升均至少 2%，
六个 seed/轮次配对至少五个为正，最差配对不低于 −1%；同时要求完整输出预算、
无 corruption、无抢占。该判据只描述这个固定负载的重复性，不代表跨节点或在线服务容量验收。
TTFT 和生成阶段延迟另外报告，不因吞吐提升就判定延迟通过。

## 配置与计时

- 单卡 B200，V2，TP1/PP1/DP1，固定 Shared-KV DSpark K8。
  balanced 30A3B target、step30000 draft；target FP8、draft/KV BF16、proposal cache FP32。
- maxlen32768、maxseq32、batched tokens2048、KV48GiB、APC 关闭。
  两组均为多进程 engine / uni executor，只改变 `async_scheduling`。
- 显式 manual MoE：Triton M≤16、Mega decode M≥17、prefill 不使用 Mega。
  阈值沿用原配置，但扩大的图集是新的实验配置，没有扩大生产自动策略的已测范围。
- target Graph tokens：9/18/36/72/135/144/261/288；
  draft：8/16/24/32/40/64/72/128/144/256。两组均核对 C32 最大图捕获和真实回放。
- C 表示一次提交的请求数，所有请求一起到达原生 LLM 前端。
  chunked prefill 会使部分请求排队，特别是长输入时；不声称全程同时有 C 条请求 decode。
- 输出吞吐为完成输出 token / GPU-drained 批次耗时，包含 prefill、decode、采样、调度和排队。
  加载、分词、预热及编译不计时，无 HTTP、无 profiler。
- 请求平均 TPOT 为 `(last_token_ts - first_token_ts)/(output_tokens - 1)`。
  speculative 更新可包含多个 token，这不是逐 token ITL 分布。

## 结果

完整 ABBA 共 **96 个正式 batch、2304 个请求、1,769,472 个输出 token**。
每格每个模式有六个正式 batch；同 seed 跨轮重复，不当成独立样本。
四轮实际均为指定的 Scheduler/容量1 或 AsyncScheduler/容量2，前端同为 SyncMPClient。

| 输入 | 输出 | C | sync tok/s | async tok/s | 汇总变化 | 第一 / 第二配对 |
| --- | ---: | ---: | ---: | ---: | ---: | --- |
| 24–38 tokens | 512 | 16 | 2856.45 | 2997.30 | +4.93% | +4.57% / +5.30% |
| 24–38 tokens | 512 | 32 | 4853.18 | 5351.27 | +10.26% | +11.11% / +9.41% |
| 24–38 tokens | 1024 | 16 | 3104.32 | 3400.31 | +9.53% | +12.08% / +7.06% |
| 24–38 tokens | 1024 | 32 | 5289.59 | 5984.56 | +13.14% | +16.37% / +10.01% |
| 16384 tokens | 512 | 16 | 460.84 | 449.18 | -2.53% | -4.50% / -0.54% |
| 16384 tokens | 512 | 32 | 475.96 | 455.12 | -4.38% | -6.16% / -2.58% |
| 16384 tokens | 1024 | 16 | 780.23 | 777.15 | -0.39% | -2.14% / +1.35% |
| 16384 tokens | 1024 | 32 | 833.92 | 816.44 | -2.10% | -4.43% / +0.29% |

短输入四格全部满足预定的重复收益判据，每格六个配对都为正。
512 输出的 C16/C32 配对范围分别为 +0.81%～+9.08% / +7.36%～+14.29%；
1024 输出分别为 +4.02%～+14.79% / +9.04%～+17.14%。
C16/512 的最弱配对只有 +0.81%，其幅度小于 C32/1024，不能都描述成十几个点的提升。

16K 输入无一格通过判据。512 输出六个配对全为负；1024 输出存在方向反转，
其中 C16 两组为 −2.14% / +1.35%，C32 为 −4.43% / +0.29%。
因此没有稳定正收益，也不把所有长输入格描述成稳定回退。
新配置的 Graph/KV/maxseq 与最初 C8 面板不同，两者不能拼成单一规模曲线。

### 延迟与接受率

| 输入 / 输出 / C | 平均 TTFT sync → async (ms) | TTFT P95 sync → async (ms) | 平均请求 TPOT sync → async (ms) |
| --- | ---: | ---: | ---: |
| short / 512 / 16 | 220.04 → 236.49 | 240.69 → 240.33 | 4.261 → 3.951 |
| short / 512 / 32 | 227.84 → 246.43 | 242.55 → 254.10 | 5.107 → 4.575 |
| short / 1024 / 16 | 232.59 → 239.89 | 298.33 → 248.90 | 4.146 → 3.764 |
| short / 1024 / 32 | 227.40 → 249.09 | 236.44 → 254.75 | 5.040 → 4.363 |
| 16K / 512 / 16 | 7956.93 → 8355.21 | 15181.68 → 15932.55 | 16.461 → 16.645 |
| 16K / 512 / 32 | 16090.89 → 16993.55 | 30701.98 → 32658.77 | 22.959 → 23.851 |
| 16K / 1024 / 16 | 8110.48 → 8383.10 | 15288.03 → 16002.79 | 10.927 → 10.797 |
| 16K / 1024 / 32 | 16559.59 → 17306.52 | 32140.92 → 33724.38 | 18.418 → 18.754 |

短输入平均 TTFT 增加约 7～22ms，平均请求 TPOT 改善约 7.3%～13.4%。
TTFT P95 并非每格都恶化，完整 P95 保留在表及 JSON 中。
16K 输入平均 TTFT 增加约 0.27～0.90 秒，生成阶段 TPOT 多数也没有改善。
这说明吞吐收益有负载和延迟取舍，不能直接等同于线上 SLO 容量提升。

各格聚合草稿接受率变化的绝对值最大约 0.37 个百分点，
没有观察到足以单独解释短输入双位数吞吐差异的接受率提升。
本轮未额外采集高并发 profile，不能把全部收益定量归因为 CPU/GPU 重叠。
原始图回放、token IDs、计数器和逐请求 metrics 均保留。

### 数值与运行回执

短输入的受控 teacher-forced 面板两组配对共 256 个 logprob 位置最大差为 0，首 token 面板也相等。
完整生成跨 sync/async 只有 **458/1152** 条配对请求逐位一致；
同模式重跑则分别为 sync **576/576**、async **576/576** 逐位一致。
调度模式之间的生成差异可重复，不能忽略，也没有完成每个分歧的逐轮因果定位。
Fast/Mega 的 batch 依赖是已知边界，但不能用它代替具体差异的正确性诊断或一般任务质量验收。

全部正式请求满足预算，metrics 中 corruption 为零、抢占为零；
32 个短 prompt 实际长度为 24～38 tokens，所有 32 个长 prompt 均为 16384 tokens。
每轮保存的 workload 完全一致，每个 profile 都有 32 个不同 prompt，C32 没有退化成八请求测试。

两组 KV 预算均为 48GiB，实际引擎报告的逻辑容量并不相同：
sync 3,730,429 tokens（maxlen32768 时 113.84x），async 2,397,637 tokens（73.17x）。
两者均高于所测 C32，实际没有容量抢占。加载后 GPU allocated 约 105.73GiB，四轮差异不足 1MiB。
两组最大 target/draft 图均实际回放，图集相同，Graph capture 日志约 0.49GiB。

## 复现与边界

大并发工具改动只涉及 benchmark：扩大独立配置预算、扩充为 32 个不同 prompt、
核对每批实际请求数和每请求输出预算、按 maxseq 检查最大图、同一 engine 扫描多个输出长度、
取消长输入正式 trial 数被隐式限制为三的行为。原 C8/KV8 默认配置保留。
没有修改 scheduler、模型、worker 或 kernel 的推理实现。

[使用说明](../ASYNC_SCHEDULING.md) 提供命令和 dispatch YAML。
原始脚本、逐请求 metrics/token IDs、日志、源码清单和原生库审计保存在
`/data/vllm_test/work/yoco-async-scheduling-20261022/attempt6/`。

当前 Fast/Mega 没有 batch-invariant 保证，固定 seed 不能保证跨调度/批次的生成逐位一致。
受控首 token / teacher-forced 面板和完整生成一致率分别保留；不能把完整输出预算、
无 corruption 或速度提升当作一般任务质量通过。

实验只适用于此单卡 30A3B/K8 配置，没有因此验证 150B、多卡、APC、P/D、grammar 或 adaptive。

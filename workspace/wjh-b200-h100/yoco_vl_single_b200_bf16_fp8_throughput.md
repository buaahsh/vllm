# YOCO-VL 单卡 B200 BF16 / FP8 高 Batch 推理速度

更新时间：2026-08-04

## 结论

- BF16 和 FP8 block-128 在 batch=32、64、96、128、192 下均成功完成，无 OOM。
- warmup 后的最高稳定吞吐出现在 batch=192：BF16 为 `8.426 req/s`、
  `269.636 output tok/s`；FP8 为 `8.328 req/s`、`266.501 output tok/s`。
- 从 batch=128 增加到 192，BF16 输出吞吐提高 3.25%，FP8 提高 4.04%；
  吞吐已接近平台期，但平均 TTFT 增加到约 7.9 秒。
- 高 batch 稳定态下 BF16 和 FP8 速度基本持平。FP8 的主要收益仍是模型权重
  显存从约 61.0 GiB 降到约 32.2 GiB，以及更大的 KV cache 容量。
- FP8 的第一轮在 batch=96/128/192 有明显的 DeepGEMM shape 冷启动开销；
  第二轮代表同一常驻引擎 warmup 后的稳定吞吐。

## 精度与后端

| 模式 | LLM linear/MoE | MoE 后端 | ViT | Projector | KV cache |
|---|---|---|---|---|---|
| BF16 | BF16，不量化 | Triton unquantized MoE | BF16 | FP32 | BF16 |
| FP8 | `fp8_per_block`，block=128，E4M3FN/E8M0 | DeepGEMM | BF16 | FP32 | BF16 |

FP8 为加载 BF16 checkpoint 时进行的在线 block-128 量化。ViT 和 projector
不量化，因此视觉编码开销不会被 FP8 加速。

## 输入构造

- 使用 4 个 image/prompt pair 循环复制到目标 batch。
- 每 4 条输入的 prompt/image token 结构与此前 batch=16 KL 实验一致。
- 平均每条输入为 `2143.25` input token。
- 为避免复制图片触发 vLLM multimodal hash/encoder cache 复用，每个请求在图片
  左上角两个像素编码唯一 ID；图片尺寸、image token 数及计算 shape 不变。
- 计时范围从调用 `llm.generate()` 开始，到完整 batch 返回结束；不包含模型加载，
  包含 CPU 多模态预处理、ViT、projector、LLM prefill 和固定 32-token decode。

## FP8 冷启动

测试沿用了此前环境中的 `VLLM_DEEP_GEMM_WARMUP=skip`。虽然每个 batch 在正式
计时前执行了 4-token shape warmup，但 FP8 在第一次完整 32-token decode 时仍有
额外的 DeepGEMM shape 初始化开销：

| Batch | FP8 第 1 轮 (s) | FP8 第 2 轮 (s) | 首轮额外耗时 |
|---:|---:|---:|---:|
| 96 | 21.446 | 12.703 | +68.8% |
| 128 | 24.890 | 15.991 | +55.7% |
| 192 | 31.931 | 23.054 | +38.5% |

因此常驻服务的稳定吞吐应参考第 2 轮；若关注服务刚启动后的首批延迟，应参考第 1
轮，或者在对外接流量前使用目标 batch 和输出长度做完整 warmup。

## 当前限制

本次使用 eager 模式，因为当前 YOCO `YOCOMoE.forward` 中的
`torch.get_float32_matmul_precision()` 返回字符串，Torch Dynamo 无法将其纳入
full graph。关闭 eager 时引擎在 profiling 阶段启动失败。因此这些数据不包含
`torch.compile`/CUDA Graph 可能带来的加速。
